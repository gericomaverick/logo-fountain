# Combined upload/lifecycle review resolution

Lifecycle source `cfbffb081ab3ef42ceaf7a1b03f4c6b53cb33e83` was cherry-picked as `ad72064` before this revision. The concept route/test conflicts were resolved with lifecycle's domain restrictions and first-publication accounting as the base, adding prepared uploads, project version fencing, and unique immutable attempts. No entitlement implementation was replaced with a parallel counter mechanism.

## Request identity and outcomes

Concept multipart POST now requires a stable UUID v4 `requestKey`. The three admin upload forms persist one key per project/action/target/notes/content hash in session storage, retiring it only after success. API consumers must retain their key until an outcome is resolved, not generate a key on each retry. Receipts bind the key to a server SHA-256 of canonical action fields, canonical MIME and exact uploaded bytes. Different content/action under an existing key returns `REQUEST_KEY_MISMATCH`.

A `concept_upload_request` audit event containing digest, result, and immutable object reference commits in the same serializable transaction as publication and usage. An existing receipt returns the original committed result before current-phase checks. PostgreSQL transaction advisory locking serializes equal project/request identities; the project status/version fence plus conditional entitlement update protects different identities. Transaction errors trigger receipt recovery. An absent/failed immediate verification **does not prove rollback**: `CONCEPT_PUBLICATION_UNCONFIRMED` includes the retained object and request key; retry the same key. Only explicitly typed callback aborts authorize cleanup of that attempt, never generic database errors. Unique `vN.UUID.ext` paths make retained-orphan retries nonblocking. Concepts and finals both forbid upsert.

Audit receipts must remain durable for the project lifetime, including after clean-slate reset; an old logical request cannot recreate reset content. Do not prune these audit event types or submit an old key to request a new publication. A receipt replay does not resend email. Notification exceptions after concept commit do not change publication success (initial response includes a warning); no email outbox/retry UI is added here.

**Deployment:** no new dependencies, schema changes, migration or live operation. Existing PostgreSQL advisory lock support and durable `AuditEvent` access through the Prisma service connection are required. Roll out updated forms/API consumers together: old callers without `requestKey` get HTTP 400. No provider responses or real PostgreSQL transaction races were exercised in this revision; focused tests use mocked database/provider boundaries.

## Lifecycle and usage policy

- Preserve lifecycle allowlists before storage and transactionally, approved/archived replacement restrictions, and atomic first publication (including draft replacement), honoring consumed **plus reserved** capacity and present-null unlimited rows.
- `status: RESUME` with a reason restores only the latest recorded pre-hold phase. It validates phase evidence (brief, visible concept, pending revision, approval, final publication as applicable), current project version, and any recorded hold version. Legacy hold events without a version can resume only with the same evidence and current-version fence. There is no arbitrary target-state argument or usage rewind. Invalid/stale evidence returns 409, not a destructive reset recommendation.
- Deletion reads/claims current status inside a serializable transaction. Repeated deletion does nothing. It never refunds consumed concepts or delivered revisions; only cancelled pending reservations are released. Approval, held/final/revision phases and the last visible concept in `CONCEPTS_READY` are protected. Use explicit clean-slate reset for a true restart.
- Alternate revision delivery conditionally claims pending-to-delivered inside the same transaction as reserved-to-consumed conversion, checking both reservation and finite capacity. Replays do not consume or notify again.
- Overrides distinguish missing from present-null, create missing unlimited rows, preserve zero-limit usage, represent `unlimited`/`configured` explicitly, and submit only edited UI fields. The numeric usage fields remain compatibility projections; consumers must honor `unlimited` rather than interpret its numeric zero as a finite cap.
- Reset confirmation explicitly includes final-publication retirement, retained stored bytes, and existing signed-link expiry. Final publication, notification-only retry and exact-asset download safeguards remain unchanged.

## ZIP acceptance and actual resource bounds

100 MiB compressed upload, at most 1,000 entries, 500 MiB **actual** total expanded bytes, and 100:1 **per-entry** actual/declaration ratio (therefore also aggregate) maximum. Stored payload sizes must agree; stored and deflated payload CRC and actual sizes are verified. Raw deflate uses Node zlib and a backpressured pipeline with 16 KiB input/output chunks; expanded archives are never accumulated. Exceeding declared size, total bytes or ratio aborts/destroys the pipeline at the next output chunk. ZIP upload bytes are still held in memory within the compressed-file limit.

Both central and local names are decoded (flagged UTF-8 or legacy CP437), compared exactly, and checked under one portable policy. Unicode name/comment override extras, ZIP64 and Unix link/special-file extras are rejected; symlink/device/FIFO/socket entries are rejected. Names must already be NFKC canonical, cannot contain traversal, backslashes, absolute/drive paths, controls, DOS device aliases or trailing dot/space components. Case-insensitive duplicates and file-as-directory collisions are rejected. Headers, CRC/size fields, signed/unsigned data descriptors and disjoint contiguous local-record ranges are verified.

Deliberate compatibility restrictions: nonempty standard single-disk ZIP only, methods stored/deflate only, no encryption, ZIP64, self-extracting prefix, digital signatures, extraneous local records/gaps or Unicode overrides. These conservative restrictions can reject extractor-valid archives; they are not claims that every rejected ZIP is malicious. Standard empty directories (including deflated empty payloads) are supported. Validity of embedded SVG/PDF/executables is **not** checked: downloaded archives are not malware-scanned or safe to execute.

## Images and delivery metadata: deliberately partial screening

Images remain 10 MiB and 40 million declared pixels maximum, allowlisted PNG/JPEG/static WebP only. PNG requires IHDR/contiguous IDAT/IEND, CRC-valid chunks, valid bit-depth/colour combinations and palettes; APNG rejected. JPEG walks all segments/scans through final EOI, checks frame/scan structure, rejects duplicate/unsupported frames and deferred dimensions. WebP walks RIFF chunks, requires an actual static VP8/VP8L payload and checks payload dimensions against the extended canvas; animation is rejected.

**This is structural/header screening, not decoder-backed image validation or canonical re-encoding.** PNG compressed pixel streams and JPEG/WebP codec payloads are not fully decoded. A structurally accepted image may still fail browser decode. Declared static dimensions and rejected animation narrow resource exposure but do not establish a complete decoder-workload guarantee. A maintained sandboxed decoder/re-encoder remains a follow-up if stronger preview guarantees are required.

Uploads set canonical MIME and cache control; arbitrary `metadata.contentDisposition` was removed because it is not an HTTP header control. Signed finals explicitly use the SDK-supported `download` option (default filename supplied); concept signed URLs are preview/inline requests without that option. Provider HTTP headers were not verified against live storage. Multipart parsing precedes application size checks: reverse-proxy/provider request-body limits remain necessary before internet deployment.

## Residual operational tradeoffs

Unknown/ambiguous outcomes and superseded immutable files are retained, potentially indefinitely; no orphan garbage collection is introduced. A lost storage-upload response may leave an untracked immutable object. Durable request receipts prevent duplicate committed logical creation, not orphan accumulation. Signed URLs already issued remain usable until expiry. Database concurrency assertions are regression-tested at mocked conditional-claim/receipt boundaries, not proven by a real database integration stress run. No deployment, live migration, provider test, browser end-to-end run, build or full test suite was performed for this combined revision.
