# Portable PostgreSQL core — staged, not a completed auth exit

No live provisioning/migrations/deletion have been authorized or run. Supabase Auth remains in this intermediate branch. The portable baseline has no Better Auth models yet and must **not** be deployed as the finished exit.

## Fresh database only

The active Prisma lineage starts with a schema-derived portable core baseline. Fourteen historical migration SQL files plus their lock are archived unchanged under `prisma/archive/supabase-migrations`; do not replay, edit, `resolve --applied` or transfer old deployment history. This is not an in-place migration or data/account/object migration. App tenant authorization is enforced by server code, **not RLS**. Runtime credentials confer broad app-table DML; never expose them to browsers or untrusted users.

With separate explicit authorization, an operator provisions an empty PostgreSQL database and roles. Example identifiers are `lf_app`, `lf_migration`, `lf_runtime`; the supplied grants template assumes `lf_runtime`. Substitute/verify identifiers consciously. Roles must be LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOBYPASSRLS, NOINHERIT with no membership in privileged roles; migration role owns database/schema/tables, runtime owns none. Use interactive `psql \password` or a secrets-management mechanism rather than putting production passwords in shell arguments/history. Use supported maintained PostgreSQL and TLS with server verification outside the loopback harness.

An authorized provisioning admin creates database `lf_app OWNER lf_migration`, revokes database privileges from PUBLIC and grants runtime CONNECT (not CREATE/TEMP). The migration owner revokes public schema CREATE from PUBLIC. These are instructions only, not a script run on operator infrastructure.

Configure DATABASE_URL with runtime role and DIRECT_URL with distinct migration owner on the **same exact normalized host, port and database**. Configuration refuses missing credentials, old Supabase hostnames/poolers, runtime fallback, different targets and libpq routing overrides before Prisma opens a connection. Host aliases/pooler names are intentionally not inferred; use one explicit target for this fresh installation. This is syntactic validation, not DNS provenance, a proof of role grants or a substitute for operator target review. Arbitrary alternate Prisma configs/psql commands are outside this safeguard; only use the documented checked entry point. Do not export migration credentials into the deployed runtime environment.

After authorization, the checked entry point is `npm run db:migrate` from apps/web; then the migration owner applies `ops/postgres/runtime-grants.sql` to the confirmed new database. Reapply/review grants after migrations. Its default privileges apply to objects created by that owner; ownership under other roles requires its own explicit grants review. Runtime has table DML and required sequence access, no schema creation, no migration-history access, no role/database creation or ownership. Backups and DDL use separate privileged operator paths, not runtime. Run a role/permission probe and schema drift check before cutover. Migrations must never be run automatically by the runtime process.

## Reproducible isolated tests

`npm run test:postgres` never reads an existing database target or downloads/install tools. Supply explicit user-local POSTGRES_TEST_BIN and POSTGRES_TEST_SHARE (and POSTGRES_TEST_LIB if bundled binaries need private shared libraries), plus PG_TEST_ARTIFACT_DIR outside the allocated cluster tree to retain sanitized evidence. The runner refuses root and .env.local overrides, allocates its own temporary cluster, selects a loopback port, uses random SCRAM credentials, provisions two constrained roles, migrates as owner, applies runtime grants, checks zero schema drift, and runs integration tests as runtime. It stops its own PostgreSQL instance and removes only its allocated cluster tree. The default unit suite skips the six opt-in PG cases; a skipped unit result is not integration proof.

Locally used PostgreSQL 18.4 binaries were acquired into /tmp from the publisher's embedded package and symlink-hydrated there, with bundled libraries supplied only to the test process. This tooling is not a production database recommendation, runtime dependency, system installation or daemon/service change. Evidence: `/tmp/supabase-exit-5649/pg-run-4/`.

Covered: real UUID schema/no RLS, least-privilege denials, 12-way last entitlement claim, 8-way advisory-locked durable request replay, simulated lost response *after a real commit* recovered through the receipt reader, digest mismatch, transaction rollback, unique paid-order session deduplication. The receipt test exercises the production helper/protocol, **not** the full HTTP upload route. Paid-order uniqueness is not full webhook fencing acceptance. Auth/token/session/reset/change concurrency and broader lifecycle/payment route integration are still unimplemented/unrun and mandatory before exit completion.
